# Sub2API 全面改进与产品演进建议

> 文档类型：产品与工程路线建议
>
> 分析基线：当前工作区源码快照（2026-10-01）
>
> 适用对象：项目维护者、后端/前端开发者、部署运营者、平台适配贡献者

## 1. 文档结论

Sub2API 已经具备“AI API 网关 + 订阅配额平台”的完整雏形，当前能力远超普通的 OpenAI 兼容转发器：

- 支持 OpenAI Responses、Chat Completions、Anthropic Messages、Gemini Native、Codex、Antigravity 等入口。
- 支持 OAuth、API Key、Setup Token、上游透传、Bedrock、Google Service Account 等账号形态。
- 已有账号池、分组、Composite、模型映射、粘性会话、并发/速率限制、失败切换、配额冷却和模型白名单。
- 已有按 Token、请求、图片、视频、搜索、音频等维度的计费能力，并接入余额、订阅、支付、兑换码和推广体系。
- 已有管理后台、实时运维面板、Channel Monitor、Prompt Audit、数据备份和插件运行时。

下一阶段最值得投入的方向不是单纯增加更多 Provider，而是把现有能力进一步产品化、标准化和可观测化：

1. 先完成已存在但仍为空实现或弱实现的关键功能，消除后台结果不可信的问题。
2. 建立统一的 Provider Adapter、模型能力和计费契约，降低新增平台的边际成本。
3. 把调度从“可用账号选择”升级为带成本、延迟、能力、风险和租户策略的智能路由。
4. 把后台日志和统计升级为可操作的故障定位、告警、对账和审计体系。
5. 面向团队和开发者提供 API 门户、预算策略、Webhook、SDK、组织空间等产品能力。

## 3. 优先级和交付原则



### 3.1 优先级定义


| 优先级 | 含义                  | 目标交付时间   | 典型内容                           |
| --- | ------------------- | -------- | ------------------------------ |
| P0  | 影响正确性、安全或收入，应立刻进入迭代 | 1-2 个小版本 | 空实现、错误计费、凭证泄漏、备份不可恢复           |
| P1  | 明显影响可用性、运营效率或新增平台成本 | 1-2 个季度  | 统一健康探测、路由解释、账本、告警、Provider SDK |
| P2  | 提升商业化、开发者体验和规模化能力   | 2-4 个季度  | 团队空间、门户、智能路由、Webhook、企业 SSO    |
| P3  | 探索性或生态性功能           | 资源允许时    | Marketplace、策略市场、边缘节点、评测平台     |




### 3.2 每个新 Provider 的准入门槛

新增平台不能只做到“能请求成功”。每个 Provider 适配至少应提交：

1. 平台身份、账号类型和凭证生命周期说明。
2. 支持的入站协议、上游协议和转换矩阵。
3. 模型目录、模型能力、上下文窗口和价格来源。
4. 非流式、流式、工具调用、视觉、长上下文、错误和取消测试。
5. 429、5xx、超时、部分响应、未知错误的重试语义。
6. 用量获取和计费回退策略。
7. 余额/配额探测是否产生费用、是否有副作用。
8. 隐私、服务条款、转售限制和 OAuth 使用边界评估。
9. 管理后台配置、测试连接、健康状态和文档。
10. 至少一个真实集成测试和一组固定回放样本。



## 4. P0：优先完成的基础修复



### 4.1 完成账号凭证测试

现状：backend/internal/service/account_service.go 的 TestCredentials 对 Anthropic、OpenAI、Gemini 仍直接返回 nil，管理员点击“测试账号”无法区分凭证无效、网络不可达、权限不足和平台限流。

建议实现：

- 引入统一的 CredentialTester 接口，按 platform + account_type + protocol 注册测试器。
- 测试分为三个等级：
  - validate_local：凭证格式、过期时间、必填字段、代理配置。
  - probe_remote：低成本、只读、最小模型目录或轻量权限探测。
  - probe_inference：可选的真实推理测试，明确可能产生费用。
- 返回结构化结果，而不是只有 error：
  ```
  status: healthy
  stage: probe_remote
  latency_ms: 328
  http_status: 200
  credential_expires_at: 2026-10-02T12:00:00Z
  capabilities: [chat, stream, tools]
  safe_to_schedule: true
  ```
- 测试时使用短超时、请求取消和脱敏日志。
- 把测试结果写入账号健康快照，前端展示测试时间、阶段、耗时、结果和建议动作。
- 不要默认调用会消耗额度的生成接口。

验收标准：

- OpenAI API Key、OpenAI OAuth、Anthropic API Key、Gemini OAuth/Service Account 至少各有成功、凭证过期、401、403、429、代理失败五类测试。
- 测试连接失败不会改变账号调度状态，除非管理员明确选择“测试失败后暂停”。
- 所有响应体和请求头中的 Token、Cookie、代理认证信息都不会进入日志。



### 4.2 完成代理连接测试

现状：backend/internal/service/proxy_service.go 的 TestConnection 获取代理后直接返回成功。

建议实现：

- 先做基础 TCP/TLS 连接，再按代理类型执行 HTTP CONNECT 或 SOCKS5 握手。
- 测试目标使用可配置的安全地址，默认只测试网关自身配置的探测域名，不允许任意 URL 造成 SSRF 风险。
- 返回 DNS、连接、TLS、首字节和总耗时。
- 显示出口 IP 时只保留管理员明确开启的字段，并限制权限。
- 代理测试和上游账号测试分离：代理能连通不代表上游凭证可用。

验收标准：

- HTTP、HTTPS、SOCKS5、SOCKS5H 代理均有覆盖。
- 代理认证失败、TLS 握手失败、DNS 失败、超时均能给出不同错误码。
- 测试接口具备管理员限流、审计和请求取消。



### 4.3 完成账号刷新逻辑

现状：RefreshAccountCredentials 仍是 TODO。OAuth 账号、Setup Token、Service Account 和带过期时间的 API 凭证缺少统一的手动刷新入口。

建议实现：

- 以 AccountCredentialRefresher 接口抽象刷新动作。
- 刷新必须使用账号级分布式锁，避免多实例同时刷新同一凭证。
- 刷新前后保留凭证版本号、过期时间和更新时间，不在审计里写密文。
- 刷新失败不立即清空旧凭证；只有明确确认 token 无效时才变更账号状态。
- 提供“刷新并验证”“仅刷新”“撤销凭证”三个不同动作。
- 对 OpenAI、Gemini、Grok 等不同 OAuth 语义分别实现，不要假设所有平台都有 refresh token。

验收标准：

- 并发刷新只产生一次上游刷新请求。
- 刷新成功后正在使用的请求可以继续完成，新的请求使用新凭证。
- 旧 Token 不出现在错误日志、任务消息、导出文件和前端响应中。



### 4.4 修复固定模拟统计

以下接口不能继续返回静态零值：

- 分组统计：backend/internal/handler/admin/group_handler.go。
- 兑换码统计：backend/internal/service/redeem_service.go。

建议优先从现有用量、用户、API Key、订单和兑换码数据聚合出可解释结果；如果数据量较大，再增加日/小时汇总表。响应中应加入：

- data_source：实时聚合、预聚合或缓存。
- generated_at：统计生成时间。
- window：统计时间窗口。
- partial：是否因超时或数据缺失而不完整。

这样前端可以明确区分“确实为 0”和“暂未实现/查询失败”。

### 4.5 明确 Live 会话计费

现状：backend/internal/service/openai_live.go 已明确记录 Live 会话目前按零成本落库，注释同时指出余额模式可能因此绕过低余额限制。

建议方案：

- 第一阶段按连接时长计费，区分 connected_seconds、active_seconds 和 audio_seconds。
- 第二阶段接入上游返回的音频输入/输出 Token 或字符量。
- 会话建立时冻结最大预计费用，结束时按实际使用结算，多退少补。
- 网络断开、进程重启、客户端取消和后台强制关闭都必须幂等结算。
- 管理后台显示 Live 的计费规则、单价、冻结金额和最终结算金额。
- 若某些 Live 渠道确实免费，增加显式的 billing_mode=free，不要靠 TotalCost 为零来表达。

验收标准：

- 同一 call_id 重复 finalize 不重复扣费。
- 中途断电或进程重启后，恢复任务能补齐未结算记录。
- 余额不足时不能无限创建长连接。



### 4.6 多实例 OAuth 临时状态集中化

auth_dingtalk_client.go 已留下 Redis 集中缓存 appToken 的 TODO。建议统一盘点所有本地内存中的 OAuth、验证码、锁、临时会话和探测状态：

- 具有跨请求、跨实例、跨重启语义的状态统一放 Redis 或数据库。
- 仅用于本实例性能优化的缓存必须有明确 TTL 和失效策略。
- 启动时打印“本地缓存/集中缓存”模式，但不打印秘密值。
- 为每个临时状态定义 key 前缀、TTL、最大尺寸和清理责任。



## 5. 对现有网关能力的改进



### 5.1 统一 Provider Adapter 契约

目前平台逻辑分散在 gateway_*、openai_gateway_*、antigravity_*、cn_provider_* 和 token provider 中。建议逐步建立以下层次：

```
Inbound Protocol
  -> Request Normalizer
  -> Routing Policy
  -> Provider Adapter
       - credential lifecycle
       - request translation
       - transport
       - response translation
       - usage extraction
       - error classification
       - health probe
       - capability catalog
  -> Billing / Usage Ledger
  -> Outbound Response
```

建议接口只表达稳定职责，不把所有平台特例塞进一个巨大接口：

- CredentialProvider：获取、刷新、撤销和脱敏摘要。
- RequestTranslator：入站协议转上游协议。
- TransportExecutor：HTTP、WebSocket、SSE、长连接和取消。
- ResponseTranslator：非流式、流式、错误和部分响应。
- UsageExtractor：从响应、响应头、异步回调或估算中提取用量。
- HealthProbe：能力、凭证、余额、配额和可调度性探测。
- CapabilityCatalog：模型和端点能力描述。

迁移时不建议一次性重写 GatewayService。可以先用 Registry 包装现有实现，新增平台先走新契约，旧平台逐步适配。

### 5.2 增加路由决策解释

当一次请求失败或性能异常时，管理员需要知道为什么选中这个账号。建议保存或采样记录：

- 入站模型、端点和请求协议。
- Composite 路由命中规则、平台、上游模型。
- 候选账号数量及每个账号被过滤的原因。
- 最终账号的健康分、优先级、并发占用、冷却状态和配额窗口。
- 是否发生重试、切换、降级、协议转换或模型映射。
- 计费模型来源和最终使用的价格版本。

向客户端只返回安全的 request_id；详细解释放管理员接口，通过权限和脱敏控制。可增加：

```
GET /api/v1/admin/ops/requests/:request_id/route-trace
```



### 5.3 重试和失败切换策略配置化

目前项目已有大量平台专属重试和错误处理。建议把规则收敛为可审计的策略对象：

- 哪些错误可重试：连接失败、超时、429、529、特定 5xx。
- 哪些错误禁止重试：明确的参数错误、余额不足、内容政策拒绝、请求已执行但响应丢失。
- 流式响应开始前和开始后的切换语义。
- 最多尝试次数、总时间预算、单账号冷却时间。
- 是否允许跨平台降级。
- 是否允许降级模型、降级协议或降级工具调用。

所有策略变更应带版本号和审计记录。默认策略继续保守，避免为了提高成功率而重复执行有副作用的请求。

### 5.4 增加幂等键和请求生命周期

建议对图片、视频、批处理、支付、Live 创建、异步任务统一支持：

- 客户端 Idempotency-Key。
- 请求状态：accepted、running、succeeded、failed、cancelled、expired。
- 请求、上游尝试、计费冻结、最终结算、输出对象之间的关联 ID。
- 重复提交时返回原任务/原结果，而不是重新调用上游。
- 幂等键作用域：API Key、用户或全局。
- 幂等键 TTL 和冲突请求体哈希校验。



### 5.5 统一流式响应和部分用量处理

流式接口最容易出现“客户端看到了输出，但系统没有完整计费”的问题。建议建立统一的 Stream Lifecycle：

1. 请求接收并冻结最低费用。
2. 上游连接建立并记录 upstream_attempt_id。
3. 首字节、首个语义事件、最后一个事件分别记时。
4. 解析终态事件、响应头和尾部 usage。
5. 客户端断开时写入 client_cancelled。
6. 上游断流时判断是否可安全切换。
7. 以估算值或部分 usage 结算，并标记 usage_source。

建议所有用量记录都带 usage_source、usage_confidence、settlement_status、pricing_version。

### 5.6 模型目录和能力目录统一化

当前项目已有模型白名单、映射、价格文件、上游同步和模型列表接口，但这些信息还可以整合成一个版本化模型目录：

- model_id、display_name、provider、family。
- 支持的 endpoint：chat、responses、messages、embedding、image、video、audio、realtime。
- 支持 stream、tools、vision、json、reasoning、computer-use、search 等能力。
- 上下文窗口、最大输出、输入/输出模态。
- 输入、输出、缓存、长上下文、搜索、音频、图片和视频价格。
- 别名、弃用时间、替代模型和可见性。
- 价格来源、更新时间和人工覆盖状态。

/v1/models 应根据 API Key 可用分组、模型白名单和实时健康状态过滤，而不是只返回静态集合。

### 5.7 请求验证前置化

将常见错误从上游失败前移到网关：

- 模型和 endpoint 组合不支持。
- 工具调用字段不兼容。
- max_tokens、max_output_tokens、thinking 参数冲突。
- 图像、音频、视频尺寸和格式非法。
- 上下文窗口超限。
- 订阅分组不允许该能力。

错误应返回稳定的机器可读 code、字段路径、可重试性和建议动作，减少平台特例泄漏给客户端。

## 6. 账号池、调度与配额改进



### 6.1 从优先级调度升级为多目标调度

在已有优先级、并发、粘性和冷却的基础上，增加可配置的多目标评分：

```
score =
  availability_weight * availability
  + latency_weight * inverse_p95_latency
  + success_weight * recent_success_rate
  + capacity_weight * remaining_capacity
  - cost_weight * estimated_cost
  - risk_weight * recent_error_risk
  - switch_weight * account_switch_penalty
```

策略必须支持：

- 按租户/分组选择成本优先、稳定性优先或延迟优先。
- 对 OAuth、API Key、付费渠道和免费渠道分别设权重。
- 粘性会话在健康下降时自动逃逸。
- 账号级和平台级预算硬上限。
- 评分输入的时间窗口和最小样本数。



### 6.2 账号租约和并发一致性

多实例下建议把账号调度从“查询后使用”进一步升级为短租约：

- Redis 原子领取租约，带 owner、request_id、过期时间。
- 请求结束或超时释放；实例崩溃由 TTL 回收。
- 同一个账号的并发、会话和长连接都通过统一租约计数。
- 租约冲突时返回候选耗尽原因，而不是泛化为 503。



### 6.3 配额窗口统一模型

不同平台已有 daily、weekly、rolling 5h、session、spark 等窗口。建议统一表示：

```
dimension: platform_or_model
window_type: rolling
window_seconds: 18000
limit: 100000
used: 42000
remaining: 58000
reset_at: 2026-10-01T16:00:00Z
source: upstream_header
confidence: high
```

这样用户端、管理员端和调度器可以共享同一份配额语义。

### 6.4 账号生命周期自动化

新增生命周期状态和自动动作：

- pending_validation：刚导入，等待凭证探测。
- healthy：可调度。
- degraded：错误率或延迟升高，降低权重。
- rate_limited：等待重置。
- credential_expiring：即将过期，触发刷新通知。
- quarantined：安全、合规或异常行为隔离。
- retired：不再接收新请求，但保留历史记录。

配套提供批量导入、批量验证、批量刷新、批量隔离和批量恢复。

## 7. 计费、账本与商业化改进



### 7.1 建立不可变费用账本

当前平台已有很多计费维度，建议把“余额变化”和“用量记录”分成两个不可变层：

- usage_event：一次调用的原始用量、上游尝试和价格快照。
- billing_ledger_entry：冻结、扣款、退款、调整、结算差额。
- balance_snapshot：为查询性能生成的当前余额快照。

每条账本记录应包含：

- 唯一业务事件 ID 和幂等键。
- 用户、API Key、分组、订阅、Provider、账号、模型、请求 ID。
- 数量、单位、单价、倍率、折扣、税费、最终金额。
- 价格版本和计算规则版本。
- 借方/贷方方向、前余额、后余额。
- 操作来源：网关、支付、兑换码、管理员、退款、补偿任务。

这样可以支持对账、重算、退款和争议处理，而不是只能依赖聚合后的 usage log。

### 7.2 冻结-结算-退款模型

对长连接、异步图片、视频、批处理和可能有延迟 usage 的平台统一采用：

1. 预估并冻结金额。
2. 任务执行。
3. 获取真实 usage 或使用估算规则。
4. 结算实际金额。
5. 释放多余冻结，或补扣差额。
6. 超时、取消、失败按策略退款。

所有步骤必须幂等，并可在后台查看完整链路。

### 7.3 价格配置治理

- 内置价格、渠道价格、分组覆盖、模型映射后的价格要明确优先级。
- 价格修改必须版本化，不能让历史账单被新价格重算。
- 价格生效时间支持未来定时生效。
- 价格变更前提供影响预览：近 7/30 天收入、成本、毛利变化。
- 价格低于成本或倍率异常时给出强告警。
- 未知模型不得静默按零价格计费。



### 7.4 对账和财务操作台

新增管理员能力：

- 上游用量与本地用量差异报表。
- 支付订单与余额入账对账。
- 账本不平衡检查。
- 失败任务冻结金额清理。
- 退款、补扣和人工调整审批流。
- CSV/Excel 导出以及按时间、用户、API Key、Provider、模型过滤。



### 7.5 支付能力增强

现有支付渠道较丰富，下一步重点是运营闭环：

- 支付回调签名、金额、币种、订单状态的统一校验器。
- 回调幂等和乱序事件处理。
- 对账任务和异常订单自动标记。
- 退款、部分退款、过期订单、重复支付处理。
- 优惠券、首充、阶梯充值、订阅自动续费和失败重试。
- 多币种展示与结算币种分离。
- 发票/收据、税率、地区限制和支付风控字段。



## 8. 运维、监控与可观测性改进



### 8.1 从业务面板补齐标准指标

建议提供 Prometheus 兼容指标和 OpenTelemetry Trace，至少包含：

- 请求量：按 endpoint、模型、平台、状态码、租户。
- 延迟：入口、排队、账号选择、连接、首字节、首 token、总时长。
- 流式：断流率、客户端取消率、部分 usage 率。
- 调度：候选耗尽、切换次数、粘性命中率、租约冲突。
- Provider：成功率、429、5xx、超时、余额不足、凭证错误。
- 计费：冻结、结算、退款、估算 usage、账本失败。
- 任务：队列长度、处理时长、失败率、对象存储读写。
- 系统：Go goroutine、内存、GC、Redis 延迟、数据库连接池、迁移状态。



### 8.2 Trace 贯穿请求链路

统一 Trace 属性：

- request.id、client.request_id、upstream.request_id。
- tenant.id、user.id、api_key.id，必要时哈希或脱敏。
- provider、account.id、model.requested、model.upstream。
- route.source、retry.attempt、billing.event_id。

请求体和 Prompt 默认不进 Trace；如需调试，采用管理员临时授权、采样比例、字段脱敏和自动过期。

### 8.3 SLO 和告警

提供默认 SLO 模板：

- 网关可用性。
- 各 Provider 成功率。
- P50/P95/P99 延迟。
- 首 Token 延迟。
- 429 比例和账号池耗尽率。
- 计费失败率。
- 异步任务最终完成率。
- OAuth 凭证即将过期数量。

告警规则要有抑制、合并、维护窗口和恢复通知，支持邮件、Webhook、企业微信、钉钉、飞书、Telegram 等通知目标。

### 8.4 故障演练和回放

新增可控的故障注入与回放工具：

- 模拟 Provider 429、529、5xx、半连接、慢响应、断流。
- 模拟 Redis 短暂不可用和 PostgreSQL 连接池耗尽。
- 回放脱敏后的请求元数据和固定上游响应。
- 验证重试、计费、日志、告警、恢复是否符合预期。

故障注入只能在显式开启的测试环境或管理员二次确认下运行。

## 9. 安全、合规与数据治理



### 9.1 凭证密钥生命周期

- 敏感字段统一使用密钥加密，区分应用密钥和数据加密密钥。
- 支持外部 Secret Manager：Vault、AWS Secrets Manager、GCP Secret Manager、KMS 等。
- 支持密钥轮换、双密钥解密窗口和批量重加密。
- 账号导出默认排除 Token、Cookie、私钥和代理密码。
- 前端只显示掩码和最后四位，不返回完整密文。



### 9.2 访问控制

将当前管理员权限进一步细分：

- 只读运维。
- 账号管理。
- 价格和计费。
- 支付和退款。
- 用户和余额。
- 安全与审计。
- 插件管理。
- 备份与恢复。

高风险操作统一要求 Step-up 2FA、审批原因和操作前后差异。

### 9.3 Prompt 和响应数据治理

- 明确默认不持久化原始 Prompt/Response。
- Prompt Audit 只保存必要的规则命中摘要和不可逆指纹。
- 允许租户配置数据驻留、保留时长和脱敏策略。
- 对图片、音频、视频对象支持生命周期清理和访问 URL 过期。
- 允许用户申请导出、删除和数据保留例外。
- 记录哪些管理员查看了敏感请求元数据。



### 9.4 SSRF、出站网络和插件边界

- 代理测试、上游 URL、Webhook、对象存储、OIDC 配置都应使用统一 URL 校验器。
- 默认禁止访问 loopback、link-local、云元数据、私网和 Unix socket，必要时白名单放行。
- Webhook 支持签名、重试、死信和目标域名白名单。
- 插件虽然是独立进程，但当前文档已明确不是操作系统沙箱，应增加权限说明、网络策略和资源配额。
- 插件 Marketplace 必须先验签、扫描、兼容性检查和人工审核。



## 10. 前端和管理后台改进



### 10.1 全局运营总览

首页和管理员 Dashboard 建议优先回答四个问题：

1. 现在有没有故障？
2. 哪个平台/账号/模型在拖累成功率？
3. 今天收入、成本、毛利和配额消耗如何？
4. 哪些凭证、支付、备份或任务需要立刻处理？

建议采用“异常优先”布局：顶部健康摘要、待处理事项、Provider 对比、成本/收入、最近变更，而不是只展示静态数字卡片。

### 10.2 账号管理工作台

- 支持保存筛选视图和批量操作模板。
- 账号导入先预览字段、冲突、风险和重复项，再正式提交。
- 批量刷新、测试、暂停、恢复、分组变更都显示进度和失败明细。
- 账号详情页展示凭证生命周期、健康时间线、配额窗口、调度原因、最近错误和用量。
- 支持“只看可调度账号”“只看即将过期”“只看最近 24 小时异常”等快捷筛选。



### 10.3 渠道和模型配置工作台

- 表单按连接、协议、模型、价格、路由、健康探测、权限分组。
- 保存前显示影响范围和变更 diff。
- 价格、模型映射、白名单支持导入导出和版本回滚。
- 为每个渠道提供“模拟请求”，并明确是否真实消耗上游额度。
- Composite 路由增加可视化匹配预览：输入模型和 endpoint 后显示最终平台、账号池、上游模型和价格。



### 10.4 用户端开发者门户

新增独立的开发者页面：

- API Key 管理和最小权限授权。
- 可用模型和能力矩阵。
- curl、Python、JavaScript、Go、Claude Code、Codex、OpenCode 示例。
- 请求日志、用量、余额、预算和限额。
- Webhook 配置和密钥轮换。
- 统一错误码、重试和流式事件文档。
- 在线健康状态和服务公告。



### 10.5 移动端和响应式

现有生态已有移动端管理控制台方向。主项目应提供稳定的只读运维 API、分页、游标、ETag、权限范围和版本化契约，减少移动端直接依赖内部接口。

## 11. 新增产品功能



### 11.1 多租户组织与团队空间

在现有用户、分组、API Key 基础上增加：

- 组织、团队、成员、角色和邀请。
- 组织级余额、订阅、预算和发票。
- 项目级 API Key 和模型权限。
- 成员级用量、成本中心和部门标签。
- 组织级 Provider 白名单和数据驻留策略。
- 组织管理员与平台超级管理员分离。

这是从“个人订阅面板”走向“团队 AI Gateway”最重要的产品扩展。

### 11.2 预算、配额和策略中心

支持按组织、用户、项目、API Key、模型、Provider、时间窗口设置：

- 金额预算。
- Token 预算。
- 请求数和并发数。
- 速率限制。
- 模型/工具/媒体能力开关。
- 超预算动作：拒绝、降级、通知、切换到低成本模型。

策略采用优先级和继承关系，后台提供最终生效配置预览。

### 11.3 智能模型路由

在 Composite 之外提供“任务级路由”：

- 根据请求能力选择支持视觉、工具、JSON、长上下文或音频的模型。
- 根据预算选择成本最低的可用模型。
- 根据延迟目标选择最快 Provider。
- 根据数据敏感级别禁止跨区域或第三方 Provider。
- 支持固定路由、加权路由、故障切换和 Shadow 流量。

第一阶段可只做规则引擎，不直接引入复杂机器学习；等数据质量足够后再做自动权重优化。

### 11.4 请求级降级与安全护栏

提供可选的降级链：

```
主模型失败
  -> 同平台同能力备用模型
  -> 其他平台兼容模型
  -> 低成本文本模型
  -> 明确拒绝并返回可解释错误
```

必须按请求类型区分：读操作可以更积极地重试，具有工具副作用的请求默认不跨模型重放。

### 11.5 Webhook 和事件总线

对外事件：

- 请求失败率异常。
- 账号凭证即将过期。
- Provider 进入熔断或恢复。
- 余额、预算、配额达到阈值。
- 支付成功、退款、对账异常。
- 异步任务完成或失败。
- 用户注册、Key 创建、管理员变更。

事件系统应支持签名、重试、去重、顺序说明、死信和手动重放。

### 11.6 轻量评测与路由质量平台

允许管理员维护固定测试集，按 Provider、模型、版本执行：

- 基础可用性。
- JSON/工具调用正确率。
- 流式格式完整性。
- 视觉/音频/多模态能力。
- 延迟、成本、成功率。
- 安全策略和内容过滤结果。

输出可以用于模型目录、渠道准入、调度权重和发布前回归测试。

### 11.7 代理缓存与语义缓存

建议先提供严格可控的请求缓存：

- 仅允许明确标记为可缓存的模型和 endpoint。
- 按租户、模型、系统 Prompt、工具定义、请求体规范化哈希隔离。
- 默认不缓存含敏感数据或实时信息的请求。
- 结果 TTL、最大对象大小、命中计费规则可配置。
- 缓存命中不应绕过权限、预算和审计。

语义缓存属于 P3，需充分评估隐私、错误答案复用和一致性问题。

在合规允许的前提下，可提供标准配置和协议兼容，而不是抓取或伪装官方客户端：

- Claude Code：Anthropic Messages、Setup Token 的合规接入。
- Codex CLI：Responses、WebSocket/Realtime、模型目录和 Fast/Flex。
- OpenCode：Zen/Go 或兼容 OpenAI 的 API。
- Continue、Cline、Roo Code、Aider、Cursor 类工具的 OpenAI 兼容配置。
- IDE 插件和内部开发助手的组织级 Key 管理。

对消费订阅账号、非公开接口、绕过官方限制的 token 或客户端伪装，应设置明确的合规准入门槛，并在 UI 中标注非官方能力和风险。

## 13. 插件生态路线

当前插件协议已经提供独立进程、签名、能力清单、UI Bridge、Host Service KV 和灰度基础。建议按以下阶段扩展：

### 13.1 Provider Transport Plugin

第一阶段允许插件扩展：

- 自定义 HTTP 上游传输。
- 自定义代理、TLS 指纹或区域路由。
- 自定义请求头和响应头处理。
- 自定义健康探测。

宿主仍负责鉴权、调度、计费和审计。

### 13.2 Full Provider Adapter Plugin

第二阶段版本化支持：

- 自定义 Provider 标识。
- 账号凭证 schema 和刷新。
- 请求/响应翻译。
- usage extractor。
- 模型和能力目录。
- 错误分类和重试建议。

插件不能自行绕过宿主的余额扣费、权限、数据留存和审计。

### 13.3 生态治理

- 官方插件签名和发布渠道。
- Marketplace 元数据、截图、兼容版本和安全声明。
- 自动化包扫描、SBOM、依赖漏洞检查。
- 插件权限声明：网络、文件、Host Service、UI Bridge。
- 插件资源配额和崩溃隔离。
- 版本回滚、灰度和停用。
- 社区插件举报、撤下和信任撤销。



## 14. 部署和规模化路线



### 14.1 先补齐生产基线

- 明确单实例、主从、水平扩展三种部署模式。
- 给出 PostgreSQL HA、Redis Sentinel/Cluster 或托管服务建议。
- 所有后台任务使用 leader election 或任务租约，避免多实例重复执行。
- 提供迁移前检查、备份校验、迁移后 smoke test 和失败恢复流程。
- 给出连接池、Redis、对象存储、日志和指标的容量估算。
- 增加只读健康检查和依赖健康检查的区分：进程活着不等于业务可用。



### 14.2 队列化后台任务

目前已有图片和运维任务，建议统一任务框架：

- 任务类型、优先级、租户、公平调度。
- 最大重试、退避、死信、取消、过期。
- worker 心跳和租约。
- 任务进度和日志。
- 结果对象存储和生命周期。
- 任务费用冻结和结算。

Redis 可以继续作为轻量队列，但任务状态和幂等记录应落 PostgreSQL，避免只依赖 Redis 内存。

### 14.3 边缘节点和区域路由

当用户和 Provider 跨区域后，可以拆分：

- Edge：鉴权、限流、请求接收、短缓存、WebSocket 接入。
- Control Plane：用户、配置、路由、计费、审计。
- Data Plane：Provider 连接、账号池和本地代理。

初期不建议立即拆微服务。可以先把边界、事件和数据契约定义清楚，再按真实瓶颈拆分。

## 19. 最终建议

如果只能选择少数几项，建议按以下顺序推进：

1. 先修复凭证测试、代理测试、刷新、统计和 Live 计费这些已知不完整功能。
2. 接着建立统一 Provider Adapter、模型能力目录、路由 trace 和 usage/计费来源字段。
3. 然后补齐账本、对账、标准指标、Trace、SLO 和告警。
4. 在基础契约稳定后集中接入一批 OpenAI 兼容平台、企业云平台和自托管平台。
5. 最后建设组织空间、预算策略、开发者门户、智能路由和插件生态。

这样做的核心收益是：以后每增加一个平台，新增的主要是配置和适配代码，而不是继续扩大网关核心分支；每一次请求失败、切换、计费和退款，也都能解释、追踪和恢复。

## 20. 进一步发现的优化点

上一版重点覆盖了网关、Provider、计费和商业化。本轮继续从生产事故、数据一致性、成本失控和长期维护角度补充以下项目。

### 20.1 P0：启动迁移前置检查与数据库恢复演练

**现状**：服务启动时会执行数据库迁移，部署文档已经说明迁移为正向流程，回滚依赖备份恢复。项目同时存在较多历史迁移和非事务索引迁移，升级失败时影响整个服务启动。

**问题**：

- 应用启动、数据库迁移、管理员可用性和后台 Worker 启动耦合在一起。
- 迁移前没有统一的数据库版本、磁盘空间、连接数和备份完整性检查。
- 仅有“备份成功”不等于“备份可恢复”。
- 多实例同时启动时，迁移锁、启动超时和流量接入顺序需要明确。

**设计**：

- 增加独立的 preflight 检查：数据库版本、迁移状态、磁盘空间、Redis 连通性、加密密钥存在性、备份年龄。
- 将启动状态拆分为 `starting`、`migrating`、`ready`、`degraded`、`failed`。
- 生产升级流程固定为：备份 -> 校验备份 -> 迁移演练/锁检查 -> 单实例迁移 -> smoke test -> 放量。
- 健康接口拆分为存活检查、就绪检查和依赖检查，不再用一个 `/health` 表达所有状态。
- 为备份增加定期恢复演练，将恢复结果、耗时、数据库版本和校验摘要写入后台。

**实现步骤**：

1. 在 setup/repository 层增加只读 preflight service。
2. 在 deploy 脚本中增加迁移前检查和失败时的明确退出码。
3. 在服务启动状态中记录 migration version、started_at、ready_at 和 failure code。
4. 增加恢复到临时 PostgreSQL 实例的自动化任务。
5. 在发布流程中加入“备份可恢复”门禁。

**验收标准**：

- 迁移前检查失败时不接收业务流量。
- 多实例只允许一个实例执行迁移，其余实例等待就绪。
- 恢复演练能够验证用户、账号、API Key、价格、支付订单和加密字段。
- 迁移失败日志包含明确的 migration name 和恢复建议，不能只返回通用启动失败。

### 20.2 P0：成本保护和异常用量熔断

**现状**：项目支持余额、订阅、倍率、图片、视频、搜索、音频和多种上游账号，但新增模型、未知模型、错误响应、长连接和并发请求可能造成成本快速增长。

**问题**：

- 用户预算、API Key 预算、分组预算、Provider 预算还没有统一的硬停止模型。
- 异常模型价格、倍率或响应 usage 可能造成意外高额扣费。
- 多个并发请求在余额检查和最终结算之间可能形成超支。
- 上游 429/5xx 风暴会增加重试量和成本。

**设计**：

- 在现有余额和订阅判断前增加预算策略层。
- 支持用户、API Key、Group、Provider、Model、Endpoint 五个维度。
- 每个维度支持日、周、月和滚动窗口。
- 超限动作分为拒绝、降级、通知、暂停 Key、暂停账号池。
- 每个请求先计算最大可能费用并冻结；无法估算时使用平台级上限。
- 未知模型、未知价格、无 usage 的高成本媒体请求默认进入人工复核或保守上限。
- 对短时间费用增幅、单 Key 并发、模型切换和重试次数建立熔断规则。

**实现步骤**：

1. 复用现有余额检查和 usage billing 流程，新增 `BudgetDecision` 而不是另起一套扣费逻辑。
2. 为请求计算 `estimated_max_cost`、`hold_cost`、`actual_cost`。
3. 将预算结果写入 usage 元数据和账本操作。
4. 增加管理员预算策略页面和模拟请求预览。
5. 先以 observe-only 统计运行，再按用户/分组灰度启用硬限制。

**验收标准**：

- 并发请求不会突破已配置的硬预算上限。
- 价格缺失时不会静默按零价放行。
- 重试失败、客户端取消、上游断流和异步任务都能释放或结算冻结金额。
- 管理员能查询“为何被预算拦截”。

### 20.3 P0：敏感数据泄漏自动门禁

**现状**：项目已有日志脱敏、Prompt Audit、管理员审计、SecuritySecret 和账号导出能力，但系统包含 Token、Cookie、代理密码、Prompt、图片、音频和支付信息，人工审查无法覆盖所有路径。

**设计**：

- 建立敏感字段词典和 canary secret 测试值。
- 对日志、错误消息、审计 detail、API 响应、导出文件、Trace、插件 UI Bridge 做统一扫描。
- 禁止以下内容进入普通日志：Authorization、access_token、refresh_token、Cookie、私钥、代理密码、原始 Prompt、完整响应。
- 对高风险日志启用结构化字段 allowlist，不允许任意 map 直接序列化。
- 对账号导出和备份下载增加 Step-up、审计、短时 URL 和下载次数限制。

**验收标准**：

- CI 中存在敏感信息泄漏测试。
- 新增字段若未经 allowlist 批准，测试失败。
- 使用 canary 值发起完整请求后，日志、数据库快照和前端响应中都找不到完整秘密。

### 20.4 P0：认证、API Key 和管理员权限的 fail-safe 检查

补充一组必须明确的安全语义：

- Redis 不可用时，认证缓存、限流和幂等分别采用什么策略。
- API Key 被禁用、过期或删除后，缓存多久失效。
- 管理员降权、删除或修改分组后，已有 JWT 和前端缓存何时失效。
- 代理转发头、真实 IP、API Key IP 白名单的信任边界。
- Simple Mode 是否会绕过余额、订阅和审计保护。
- 账号组权限变更是否立即影响正在执行的请求。

建议统一增加 `authz_decision`、`cache_source`、`policy_version` 和 `deny_reason` 元数据，并为所有 fail-open 行为建立显式配置，默认 fail-close。

### 20.5 P1：配置版本、配置漂移和多实例失效

**现状**：系统有大量 YAML、环境变量、数据库 Setting、账号 JSON、分组 JSON 和前端配置，部分配置支持动态修改，部分配置只在启动时读取。

**问题**：管理员看到的配置可能与运行中的内存快照、其他实例和实际 Provider 行为不一致。

**设计**：

- 为运行时配置增加 source、version、updated_at、updated_by、effective_at。
- 配置来源明确优先级：启动环境、YAML、数据库设置、账号/分组覆盖、请求级参数。
- 动态配置保存采用版本 CAS，发布 Redis invalidation，实例加载失败时保留最后有效快照。
- 管理后台显示“数据库值、当前实例生效值、集群版本、未同步实例”。
- 支持配置 diff、回滚和未来生效时间。

**验收标准**：

- 两个管理员同时修改同一配置时不会静默覆盖。
- Redis 通知丢失后，实例仍能通过 TTL 或版本轮询最终收敛。
- Provider 请求能关联到实际生效的配置版本。

### 20.6 P1：数据库查询、索引和大表生命周期治理

**现状**：项目已有大量迁移、usage 日志、错误日志、监控历史、支付审计和聚合表，且部分数据支持分区、归档和保留清理。

**新增建议**：

- 建立每张高增长表的保留周期、分区策略、归档目标和删除负责人。
- 为 Dashboard、Usage、Ops、Channel Monitor 的主要查询建立 EXPLAIN 基线。
- 对分页统一使用稳定排序和游标，避免深分页扫描。
- 对后台批量列表增加最大时间跨度、最大页大小和超时边界。
- 对 JSONB 查询建立必要的表达式索引，避免无条件全表扫描。
- 把清理任务拆为小批量、可恢复、可观测的任务，并记录删除水位。

**验收标准**：

- 主要查询在百万级 usage 数据上有明确 P95 上限。
- 清理任务失败可重试，不阻塞主请求。
- 任何归档或删除都能根据 audit/operation id 追踪。

### 20.7 P1：Provider 健康不只看“请求成功”

完善 Channel Monitor 和账号健康模型，区分：

- 凭证有效。
- 网络可达。
- 模型存在。
- 模型支持目标 endpoint。
- 工具调用可用。
- 流式格式正确。
- usage 可提取。
- 余额/配额可读取。
- 延迟满足 SLO。
- 内容安全或区域策略允许。

每项使用独立健康维度，调度器根据请求能力选择健康账号，避免一个简单 200 响应覆盖所有问题。

### 20.8 P1：模型目录和价格表的变更审批

模型价格、上下文和能力是计费与路由的事实来源，不应只依赖手工 JSON 或后台随意修改。

建议：

- 模型目录和价格使用版本号。
- 变更必须通过 schema 校验。
- 价格变更提供影响预览。
- 新模型先进入 disabled 或 canary 状态。
- 支持生效时间和回滚版本。
- 保留价格来源、抓取时间、人工审批人和发布批次。

### 20.9 P1：统一错误码和客户端可重试语义

当前不同 Provider 和协议有大量错误转换。建议统一内部错误分类：

- auth_invalid
- auth_expired
- permission_denied
- request_invalid
- model_unavailable
- quota_exhausted
- rate_limited
- upstream_overloaded
- upstream_timeout
- transport_failed
- response_invalid
- billing_blocked
- policy_blocked
- retry_exhausted

对外响应保留 OpenAI、Anthropic、Gemini 等协议格式，但统一附加安全的内部 code、request_id、retryable 和 retry_after。

### 20.10 P1：请求回放和最小可复现诊断

新增“诊断包”概念，只包含：

- 请求元数据。
- 模型和 endpoint。
- 路由决策摘要。
- Provider 和账号匿名标识。
- 错误码和时间线。
- 脱敏后的请求结构摘要。
- 上游响应状态和 usage 摘要。

默认不包含原始 Prompt、Token 和完整响应。管理员可导出诊断包用于本地回放，回放环境禁止真实扣费和真实上游写操作。

### 20.11 P1：升级、回滚和版本兼容矩阵

项目支持在线升级、Docker、systemd 和 Apple container，多种部署方式容易产生版本漂移。

建议建立：

- 应用版本、数据库迁移版本、前端资源版本、插件版本的兼容矩阵。
- 启动时报告当前版本组合。
- 升级前检查未完成任务、未结算账单、活跃 WebSocket、备份和磁盘空间。
- 新旧 API 和插件协议的兼容周期。
- 数据库迁移不可逆时的回滚手册。
- 发布包 checksum、签名和 SBOM。

### 20.12 P1：后台任务统一死信和人工处理台

已有图片 Worker、Usage Worker、Monitor、Aggregation、Cleanup、Outbox 等多个后台任务体系，建议统一展示：

- 队列深度。
- 正在处理数量。
- 失败数量。
- 重试次数。
- 下次重试时间。
- 死信数量。
- 最后成功时间。
- 最后错误码。

管理员可以查看任务详情、暂停任务、重试单条、批量重试和标记人工处理，但不能直接绕过幂等和账务状态。

### 20.13 P2：用户/API Key 的生命周期和成本归属

增加 API Key：

- 创建者。
- 项目归属。
- 权限范围。
- 允许模型。
- 允许 endpoint。
- 预算。
- IP/地域限制。
- 最近使用时间。
- 即将过期提醒。
- 最后一次错误。
- 轮换版本。

支持 Key 双版本并行轮换、旧 Key 宽限期、自动吊销未使用 Key 和成本中心归属。

### 20.14 P2：前端请求一致性和离线恢复

前端已有缓存、请求去重、Token 刷新和部分 ETag 能力，继续补充：

- 所有列表请求支持 AbortSignal。
- 页面离开时取消不再需要的请求。
- 防止旧请求覆盖新筛选结果。
- 批量操作采用任务 ID 和进度查询，而不是长时间阻塞页面。
- 失败操作保留可重试上下文。
- Token 刷新、权限变化和多标签页状态变化统一处理。
- 关键写操作显示服务端最终状态，避免只根据乐观 UI 判断成功。

### 20.15 P2：Provider 合规和账号来源登记

每个账号增加来源与合规元数据：

- 官方 API Key。
- 官方 OAuth。
- 企业合同账号。
- 自托管服务。
- 第三方聚合平台。
- 未确认来源。

后台显示是否允许转售、是否允许共享、数据区域、隐私条款和风险等级。高风险来源默认不可加入商业订阅分组。

### 20.16 P2：多区域和数据驻留策略

在引入更多 Provider 后，增加请求级数据策略：

- 允许的区域。
- 禁止跨境的 Provider。
- 允许的账号代理区域。
- Prompt 是否允许出境。
- 图片/音频对象存储区域。
- 审计日志存储区域。

先做配置和路由拒绝，不立即拆多区域微服务。

### 20.17 P3：智能路由、语义缓存和自动调参

这些功能建立在高质量请求、延迟、成本和结果数据之上，必须后置：

- 成本/延迟/成功率自动权重。
- 任务级模型选择。
- 语义缓存。
- 自动 Provider 权重学习。
- 自动价格建议。
- 自动故障预测。

在没有稳定账本、Trace 和能力目录前，不建议优先投入。

## 21. 轻重缓急总排序

### 21.1 立即处理：P0，先解决会造成事故、损失或错误数据的问题

| 顺序 | 项目 | 原因 | 第一版完成标志 |
| --- | --- | --- | --- |
| P0-1 | 迁移前置检查、备份校验、恢复演练 | 升级失败可能导致整个服务不可用，且数据恢复是最终兜底 | 能在临时数据库恢复并验证关键业务数据 |
| P0-2 | Live、异步媒体和长请求的成本保护 | 长连接和媒体请求可能绕过普通余额/usage 路径 | 有冻结、结算、释放和超支拒绝 |
| P0-3 | 账号凭证测试、代理测试、账号刷新 | 当前后台存在空实现，运营判断不可信 | 管理员能得到结构化、可追踪的测试结果 |
| P0-4 | 敏感数据泄漏门禁 | Token、Prompt、Cookie 和代理凭证一旦泄漏无法补救 | CI canary 扫描和日志 allowlist 通过 |
| P0-5 | 认证、API Key、管理员权限 fail-safe | Redis 缓存或权限变更异常可能扩大访问范围 | 权限失效、缓存失效和降级语义有测试 |
| P0-6 | 分组和兑换码真实统计 | 固定零值会直接误导运营和财务 | 统计有真实数据源、时间窗和生成时间 |
| P0-7 | 账号过期、限流、恢复状态统一 | 账号池状态错误会造成大量失败或错误重试 | 生命周期状态、自动暂停和人工恢复可追踪 |

### 21.2 近期处理：P1，先建立可扩展和可排障基础

| 顺序 | 项目 | 原因 | 第一版完成标志 |
| --- | --- | --- | --- |
| P1-1 | 配置版本、CAS、集群失效和配置漂移 | 多实例下最容易出现“后台显示与实际运行不一致” | 能看到生效版本、实例同步状态和回滚记录 |
| P1-2 | Provider Adapter Registry | 后续每加一个平台都会触碰核心网关 | 新 Provider 只实现适配器和能力目录 |
| P1-3 | 模型能力和价格目录 | 路由、模型列表和计费都依赖它 | 模型、能力和价格均有版本、来源和回滚 |
| P1-4 | Route Trace 和统一错误码 | 没有解释链路就无法快速排障 | 管理员能解释一次请求为什么选账号、重试和计费 |
| P1-5 | 统一使用量来源和结算状态 | 流式、异步和媒体容易出现漏计费/重复计费 | 每笔费用可追踪到 usage source 和 price version |
| P1-6 | 数据库查询、索引和大表生命周期 | usage、ops、monitor 数据会持续增长 | 有保留、归档、清理水位和 EXPLAIN 基线 |
| P1-7 | Provider 多维健康探测 | 单次 200 不能证明工具、流式、配额都可用 | 调度器按能力维度选择健康账号 |
| P1-8 | 统一后台任务、死信和人工处理 | 多种 Worker 已存在但运维入口分散 | 所有任务都有状态、租约、重试和死信 |
| P1-9 | OpenAPI、兼容矩阵、诊断包和请求回放 | 降低用户接入和问题复现成本 | 可导出脱敏诊断包并按版本回放 |
| P1-10 | SLO、指标、Trace 和告警 | 只有业务页面无法做可靠运营 | 能按 Provider、模型、账号定位延迟和错误 |
| P1-11 | 升级兼容矩阵和发布门禁 | 多部署方式和多迁移版本容易产生升级事故 | 发布前验证 checksum、迁移、插件和恢复 |
| P1-12 | 先接入少量标准 API Provider | 用于验证 Adapter 抽象是否可用 | 至少一个标准聚合平台通过完整契约测试 |

### 21.3 中期处理：P2，提升商业化和团队使用体验

| 顺序 | 项目 | 原因 | 第一版完成标志 |
| --- | --- | --- | --- |
| P2-1 | 预算、项目和成本中心 | 让团队能安全使用，而不是只靠余额 | 项目/API Key 有预算和超限动作 |
| P2-2 | API Key 生命周期和最小权限 | 降低共享 Key、长期 Key 和泄漏风险 | Key 可轮换、过期、限模型和限 endpoint |
| P2-3 | 组织、团队和 RBAC | 从个人订阅扩展到团队和企业 | 组织管理员不能越权访问平台超级管理员功能 |
| P2-4 | 开发者门户、SDK 和 CLI | 降低接入、排障和运营支持成本 | 用户可自助获取文档、Key、模型和用量 |
| P2-5 | 自托管 Provider：Ollama/vLLM/SGLang | 扩展私有化和数据不出网场景 | 支持模型同步、健康检查和容量调度 |
| P2-6 | 企业云 Provider：Azure/Bedrock/Vertex 增强 | 满足企业采购和区域部署 | 有区域、IAM、部署名和配额支持 |
| P2-7 | 价格审批、影响预览和收益报表 | 降低人工改价造成的收入风险 | 价格变更可预览、审批、定时和回滚 |
| P2-8 | 多区域和数据驻留策略 | Provider 增多后合规需求自然出现 | 请求可按区域和数据策略拒绝或路由 |
| P2-9 | 前端任务中心、批量操作和离线恢复 | 提升管理大量账号和任务的效率 | 批量操作可追踪、可重试、可恢复 |
| P2-10 | Provider 来源和转售合规登记 | 避免把高风险账号放入商业分组 | 账号来源、区域和风险等级可审计 |

### 21.4 后期探索：P3，基础设施稳定后再做

| 项目 | 后置原因 |
| --- | --- |
| 智能模型路由和自动调权 | 没有稳定的成本、延迟、成功率数据时容易误调度 |
| 语义缓存 | 涉及隐私、答案一致性、实时信息和计费边界 |
| Provider Marketplace | 需要插件沙箱、签名、扫描、权限模型和生态治理 |
| 边缘节点和多区域控制面 | 只有单体性能和数据边界明确后才值得拆分 |
| 自动故障预测 | 需要长期、可靠、统一的指标和事件数据 |
| 自动价格建议 | 必须建立真实成本、收入和利润账本 |
| 复杂策略市场 | 需要成熟 RBAC、版本、审计和回滚能力 |

## 22. 最终执行顺序

建议不要同时启动所有方向，采用以下顺序：

1. 先做 P0-1 到 P0-7，目标是数据不丢、钱不乱、权限不越权、后台结果可信。
2. 再做 P1-1 到 P1-6，目标是配置、模型、价格、路由和计费可解释。
3. 接着做 P1-7 到 P1-12，目标是 Provider 可扩展、任务可运维、故障可定位。
4. 基础稳定后做 P2-1 到 P2-4，目标是组织化、商业化和开发者自助接入。
5. 按客户需求选择 P2-5 到 P2-10 的平台和企业能力。
6. 最后再评估 P3 智能路由、语义缓存、Marketplace 和多区域架构。

判断是否可以进入下一阶段的门槛：

- P0 阶段未完成前，不扩展大量新 Provider。
- 没有价格版本和结算状态前，不上线自动降级和智能路由。
- 没有配置版本和回滚前，不开放复杂的动态策略。
- 没有备份恢复演练前，不做大规模数据库迁移。
- 没有插件权限和签名治理前，不开放第三方 Marketplace。
